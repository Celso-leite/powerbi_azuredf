1. PROBLEMA RAIZ
================================================================================

O Azure Data Factory possui um recurso chamado Automatic Connector Upgrade que
pode migrar conectores antigos para versoes mais novas em modo de
compatibilidade, dependendo do conector, do Integration Runtime e do cenario.

No ambiente atual, os 3 Linked Services PostgreSQL usam o tipo PostgreSqlV2.
Para este tipo de Linked Service, a documentacao atual da Microsoft nao lista
o campo "version" como propriedade valida. O campo "version": "2.0" aparece no
conector AzurePostgreSql, que e um tipo diferente de conector.

Assim, a correcao NAO deve adicionar "version" aos Linked Services
PostgreSqlV2. O ponto fragil a corrigir e o uso de queries compostas
"SET statement_timeout; SELECT ...", deixando o timeout nas propriedades
documentadas do ADF: queryTimeout no Copy source e commandTimeout no Linked
Service.

O comportamento observado no conector atual quebrou dois pontos:

  a) Queries compostas com "SET statement_timeout; SELECT ..."
     O novo conector embulha a query do usuario em subconsultas para extrair
     metadados, quebrando instrucoes compostas. Isso fez com que colunas
     existentes fossem reportadas como inexistentes (ex: "column anomes_venda
     does not exist") e datas fossem retornadas como null.

  b) Serializacao de tipos de dados no Parquet
     Campos date do PostgreSQL passaram a ser serializados com tipo incorreto,
     gerando valores nulos em datas e valores monetarios inflados (trilhoes).

Resultado: particoes 202605 e 202604 corrompidas nos arquivos Parquet do
Data Lake com 100% de datas em branco e valores absurdos.

Nota tecnica:
  - PostgreSqlV2Source suporta queryTimeout no source da Copy Activity.
  - PostgreSqlV2 Linked Service suporta commandTimeout.
  - Quando queryTimeout e commandTimeout coexistem, queryTimeout tem
    precedencia para a query da Copy Activity.

--- 2.2 PIPELINES COM SET statement_timeout ---

O SET statement_timeout e uma instrucao PostgreSQL para definir timeout de query.
O novo conector nao suporta instrucoes compostas (SET + SELECT na mesma string).
A correcao e remover o SET das queries e usar os timeouts documentados do ADF:
queryTimeout no PostgreSqlV2Source e commandTimeout no Linked Service.

Os timeouts usados nos pipelines sao:
  - 1800000ms = 1800 segundos (30 min) - dimensoes, metas, tarefas, rodada
  - 2400000ms = 2400 segundos (40 min) - fatos e dimensoes incrementais

Observacao sobre o estado atual:
  - A maioria dos Copy sources ja possui queryTimeout configurado.
  - Fatos e dimensoes incrementais usam queryTimeout de 01:00:00.
  - Metas usam queryTimeout de 02:00:00.
  - Tarefas, rodada e varias cargas menores usam queryTimeout de 00:30:00.
  - Portanto, o ajuste principal das queries e remover o SET; o
    commandTimeout do Linked Service e uma configuracao complementar.

6. OBSERVACOES IMPORTANTES
================================================================================

  - Com servicos parados nao ha risco de conflito durante a migracao
  - A combinacao queryTimeout no Copy source + commandTimeout no Linked
    Service substitui o SET statement_timeout das queries - nao e necessario
    manter os dois
  - Quando queryTimeout e commandTimeout coexistem, queryTimeout tem
    precedencia na execucao da query da Copy Activity
  - Nao adicionar campo "version" aos Linked Services PostgreSqlV2; esse
    campo pertence ao conector AzurePostgreSql, nao ao PostgreSqlV2 usado
    neste repositorio
  - O pipeline pl_fatopromocaodesconto.json nao usa SET e nao precisa de
    alteracao - investigar separadamente a questao do Desconto Promocao BEES
  - Os pipelines _copy1 e _v1 provavelmente nao rodam em producao mas devem
    ser corrigidos para evitar confusao futura
  - Apos a migracao, monitorar Service Health > Health Advisories no portal
    Azure para receber notificacoes sobre futuras deprecacoes de conectores

7. PONTOS ADICIONAIS - REVISAO CONTRA DOCUMENTACAO OFICIAL (18/05/2026)
================================================================================

Revisao realizada apos execucao dos ajustes. Fonte: documentacao Microsoft Learn
para Azure Data Factory PostgreSqlV2 (atualizada fev/abr 2026).

--- 7.1 CONFIRMACOES ---

Os seguintes pontos do plano foram confirmados pela documentacao oficial:

  - commandTimeout e propriedade valida e documentada para PostgreSqlV2 Linked
    Service. Descricao oficial: "The time to wait (in seconds) while trying to
    execute a command before terminating the attempt and generating an error.
    Set to zero for infinity."

  - queryTimeout no Copy Source tem precedencia sobre commandTimeout: "If both
    commandTimeout and queryTimeout are configured, queryTimeout takes
    precedence." (confirmado pela doc)

  - O campo "version" nao pertence ao PostgreSqlV2 Linked Service; esta correto
    nao adiciona-lo.

  - trustServerCertificate e propriedade valida e documentada; preservar em
    PostgreSupabase_rodada_negocio.json esta correto.

  - A remocao do SET statement_timeout das queries e a correcao adequada; o
    conector V2 nao suporta queries compostas (multiplas instrucoes na mesma
    string).

--- 7.2 PONTO CRITICO - DECIMAL (PRECISION > 28) NAO SUPORTADO NO V2 ---

A documentacao explicita que o tipo Decimal com precisao acima de 28 e
UNSUPPORTED no conector V2:

  PostgreSqlV2: Decimal (Precision > 28) -> NAO SUPORTADO
  PostgreSqlV1: Decimal (Precision > 28) -> String

  A alternativa documentada e usar to_char() na query para converter o campo
  para String antes da copia:
    Exemplo: to_char(coluna_numeric, 'FM999999999999999999.99')

  Risco: se alguma view/tabela usada pelos pipelines possuir colunas NUMERIC
  com precisao > 28, a Copy Activity falhara ou gerara valores nulos sem erro
  explicito, dependendo do contexto.

  ACAO OBRIGATORIA ANTES DO REPROCESSAMENTO:
  Executar a query abaixo no Supabase para auditar colunas afetadas:

    SELECT table_name, column_name, data_type, numeric_precision, numeric_scale
    FROM information_schema.columns
    WHERE table_schema = 'public'
      AND data_type IN ('numeric', 'decimal')
      AND numeric_precision > 28
    ORDER BY table_name, column_name;

  Se retornar linhas, aplicar to_char() nas queries correspondentes antes de
  reprocessar as particoes corrompidas.

--- 7.3 MUDANCAS DE MAPEAMENTO DE TIPO QUE PERSISTEM APOS A CORRECAO DO SET ---

Estas alteracoes sao do conector V2 em si e ocorrem independentemente da
correcao do SET statement_timeout. Podem ser causa adicional ou complementar
dos valores absurdos observados nas particoes corrompidas:

  Tipo PostgreSQL         | V1 (interim type) | V2 (interim type)
  ----------------------- | ----------------- | -----------------
  Money                   | String            | Decimal
  Timestamp with timezone | String            | DateTime
  Time with timezone      | String            | DateTimeOffset
  Interval                | String            | TimeSpan

  Impacto pratico:
  - Colunas Money agora chegam como Decimal no Parquet. Se havia logica no
    Power Query ou DAX que tratava Money como String (ex: conversoes manuais,
    replace de simbolo de moeda), pode necessitar ajuste.
  - Timestamp with timezone agora e DateTime; verificar se os dados de data/hora
    com fuso chegam corretamente no modelo semantico.

  ACAO: apos o reprocessamento das particoes 202604 e 202605, validar as colunas
  de tipo Money e Timestamp with timezone nas tabelas de fato e dimensao.

--- 7.4 TIPO DE DATASET - DÍVIDA TECNICA ---

A documentacao indica que datasets do tipo RelationalTable (V1) e sources do
tipo RelationalSource (V1) continuam funcionando no conector V2, mas estao
marcados como "still supported as-is, while you are suggested to use the new
one going forward."

  Tipos antigos (V1, funcionam mas nao recomendados):
    Dataset: RelationalTable
    Source:  RelationalSource

  Tipos novos (V2, recomendados):
    Dataset: PostgreSqlV2Table
    Source:  PostgreSqlV2Source

  Nao e bloqueante para o incidente atual; pode ser corrigido oportunisticamente
  em uma sprint futura para eliminar a dependencia de compatibilidade.

--- 7.5 SINAL DE VALIDACAO POS-PUBLISH - autoUpgrade ---

O ADF registra no output de cada Copy Activity se a atividade foi
automaticamente migrada pelo Automatic Connector Upgrade:

  "source": {
      "type": "PostgreSqlV2",
      "autoUpgrade": "true"
  }

  Apos a publicacao da correcao, esse campo NAO deve mais aparecer nos logs das
  execucoes. Se "autoUpgrade": "true" ainda aparecer em alguma atividade, indica
  que aquela atividade nao recebeu a correcao corretamente.

  Usar como checklist de validacao pos-Publish: inspecionar o output das
  atividades de Copy nas primeiras execucoes apos a migracao.

--- 7.6 REQUISITO DE VERSAO DO POSTGRESQL ---

O conector PostgreSqlV2 suporta apenas PostgreSQL versao 12 e acima. O Supabase
atual opera em PostgreSQL 15+, portanto nao ha risco. Registrado aqui para
referencia em eventuais migrações futuras de ambiente.

--- 7.7 SENSIBILIDADE A MAIUSCULAS EM NOMES DE SCHEMA/TABELA ---

A documentacao alerta: "Schema and table names are case-sensitive. Enclose them
in double quotes in the query."

  Nas queries existentes os nomes estao em letras minusculas e sem aspas duplas
  (ex: SELECT * FROM public.fatoestoqueatual_pbi), o que e seguro pois o
  PostgreSQL faz fold para lowercase em identificadores nao citados entre aspas.

  Risco residual: se existir alguma query com nomes de tabela em CamelCase sem
  aspas duplas, ela pode falhar. Verificar oportunisticamente ao revisar queries
  do pl_metas.json e outros pipelines com queries estaticas.
